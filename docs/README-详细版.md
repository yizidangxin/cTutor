# ctutor — C 语言报错解释器

> **定位：只解决「编译不过、看不懂」，不解决算法、调试、考试。**
> 凡是帮人读懂报错的功能保留；凡是替人改代码的功能一律不是主路径——
> 因此 `check` **永远不会修改你的代码**，`fix` 是需要显式调用的实验性子命令。

面向中文初学者的 C 语言报错解释工具。Python + 命令行 + 本地知识库优先，AI 只兜底。

---

## 快速开始

**最简单：双击桌面上的「C语言报错助手」图标。** 不会弹黑框，打开就能用。

> 图标丢了或项目移动了？在项目目录运行一次即可重建：
> ```bash
> python tools/make_shortcut.py
> ```
> 备用入口：项目目录下的 `启动面板.bat`。

命令行方式（面板与命令行共用同一套引擎）：

```bash
python panel.py                      # 启动面板
python panel.py 你的代码.c            # 直接打开某个文件
python panel.py --selftest shot.png  # 离屏渲染截图（无人值守验证用）

# 命令行（零第三方依赖，不装 PySide6 也能用）
python cli.py doctor            # 环境与配置自检（加 --ai 测 DeepSeek 连通性）
python cli.py kb                # 知识库统计 + Top-20 高频命中率

# 主路径：只解释，不改代码
python cli.py check 你的代码.c            # 分层讲解（默认 4 层）
python cli.py check 你的代码.c --brief    # 只给结论
python cli.py check 你的代码.c --depth 3  # 讲到「原因」为止
python cli.py check 你的代码.c -o report.json   # 结构化报告（供界面/统计）
python cli.py check 你的代码.c --ai       # 知识库没收录时让 DeepSeek 补充

python cli.py pending           # 待补清单：未收录的错误码按出现次数排序
python cli.py fix 你的代码.c --dry-run   # [实验性] 超出定位，默认不用
```

**依赖情况**：命令行只用标准库；图形面板需要 `PySide6` 与 `qtmonaco`
（国内务必用镜像装，直连 PyPI 实测只有约 0.6 MB/min）：
```bash
pip install -i https://pypi.tuna.tsinghua.edu.cn/simple PySide6 qtmonaco
```

配置密钥：见下方「如何接入 AI」。**不要把密钥写进代码或提交到仓库。**

## 打包分发给别人

```bash
python tools/build_package.py                # 完整打包（含便携编译器）
python tools/build_package.py --no-toolchain # 不捆绑编译器（体积小很多）
python tools/build_package.py --skip-build   # 跳过 PyInstaller，只重组目录
```

产物是 `_pack/ctutor-<版本>-便携版.zip`，对方**解压后双击 `ctutor.exe` 即可**——
不需要装 Python，不需要装编译器，不需要管理员权限，不写注册表。

| 项 | 说明 |
|---|---|
| 入口 | 打包时以 `main.py` 为入口：不带参数开图形面板，带子命令走命令行 |
| 程序根目录 | 冻结后 `config.ROOT` 取 **exe 所在目录**，而不是 PyInstaller 的临时解压目录——否则 `log/`、`build/` 会写进临时目录，程序一关就没了 |
| 自带编译器 | 捆绑 [w64devkit](https://github.com/skeeto/w64devkit)（便携 GCC），对方机器上没编译器也能用 |
| 体积 | w64devkit 解压后 708MB，脚本会砍掉对纯 C 教学无用的部分（32 位运行时、CMake、C++/Fortran 前端、gdb、文档），砍到约 360MB |
| 自动验证 | 打包完会**运行打包出来的 exe 做离屏自检**：能否启动、Monaco 是否加载、能否真编译一个样本、讲解是否命中。任一不通过就明确报错，不会让你把坏的包发出去 |

> **打包踩到的坑（都已在代码里处理）**
>
> 1. **Windows 的 260 字符路径上限**（真实事故：朋友从微信下载目录直接运行，报
>    `Failed to load Python DLL ... LoadLibrary: 找不到指定的模块`）。
>    根因是包内最深路径 +145 字符，加上对方的目录前缀达到 303 字符 ——
>    **超出上限后 Windows 自带解压器会静默跳过文件**，解压出来的包本身就已经是残的。
>    处理：删掉 C++ 头文件（那条最深的链，纯 C 教学用不到）、`bin\w64devkit` 改名
>    `bin\gcc`，最深降到 +79；包名与目录名改成纯 ASCII；
>    并在包里放一个**不依赖 exe 的自救脚本** `检查是否路径太长.bat`（exe 起不来时它还能跑）。
>    实测：在 152 字符的深目录下解压完整（4000 个文件）且运行正常。
> 2. **qtmonaco 会启动 Python LSP 服务**：它在构造编辑器时执行 `sys.executable -m pylsp`。
>    打包后 `sys.executable` 就是本程序自己——会变成"启动自己"。已在 `panel.py` 里覆盖
>    `get_pylsp_host` 拦掉，并在 spec 里排除整套 LSP 依赖（顺带省掉几十 MB）。
> 3. **`pythonw` / windowed exe 下 `sys.stdout` 是 `None`**：直接 `print` 或
>    `sys.stdout.reconfigure` 都会崩，而且**异常是静默的**（双击没反应）。已加防护 +
>    崩溃日志 + 自检结果写 JSON 文件（无控制台也能做自动化验证）。
> 4. **GCC 需要可写的临时目录**：受限环境下 gcc 会直接失败并输出
>    `Cannot create temporary file in ...: Permission denied`，表现为"一条诊断都没有"。
>    已把 `TMP/TEMP/TMPDIR` 指到工作目录下。
>
> **验证这类问题的方法论**：一开始我用**目录联结**去模拟长路径，结果两次"复现"都
> 不可靠（联结是重解析点，行为和真实目录不同）。改用**真解压**之后才看清真相：
> 解压日志里成百条 `ExtractToFile: Could not find a part of the path ...`，
> 直接指向"解压器静默跳过超长路径文件"这个根因。

### 一键运行

![运行输出](docs/screenshots/panel_full_run.png)

**只有一种方式：F9 直接跑，输出显示在「运行输出」页——不弹黑色命令行窗口。**

| 操作 | 结果 | 适合 |
|---|---|---|
| **F9** / 工具栏「运行」 | 先编译，通过后运行，输出**边跑边显示**到「运行输出」页 | 日常用；连续计算超过设定秒数自动终止（防死循环） |
| 命令行 | `python cli.py run 你的代码.c --input "3 4"` | 脚本化 |

**程序要输入（`scanf`）怎么办**：两种都行。

1. **先填好再按 F9**：把要输入的内容填进「程序输入」框（每行一个），按 F9 一次性喂给它。
2. **边跑边答（半交互）**：程序运行中，在同一个输入框里打字、按**回车**（或点「发送」），
   这一行就立刻送进正在运行的程序，程序问一句、你答一句，像在终端里一样——
   只是**没有黑色命令行窗口**。你输入的内容会以 `› ` 开头回显在输出里，
   因为标准输入是管道，程序不会自己把收到的字打回屏幕上。
3. **结束输入（EOF）**：程序用 `while (scanf(...) != EOF)` 这类写法时，必须读到"没有更多输入了"
   才会往下走。这时点页签栏右边、紧挨「运行输出」的**「结束输入 (EOF)」**按钮，
   或者**把输入框清空后直接按回车**，效果一样（相当于终端里的 Ctrl+Z）。

**编译不通过就不运行**——代码得先能编译，才谈得上运行。

> **等输入的时间不算超时**：超时统计的是"程序真的在跑"的时间——CPU 在转、或者有新输出。
> 程序停在 `scanf` 上等你敲键盘时，这段"等人"的时间一秒都不计入，所以**想多久都行**：
> 去倒杯水回来再输，程序照样活着。（死循环把 CPU 吃满，依旧会在设定秒数后被终止。）
> 真要中止一段算不完的程序，点页签栏右边的**「停止」**，立刻连子进程一起杀掉。

> **「程序输入」框是跟着文件走的**：每个标签各记各的输入。开了两个项目、
> 在 A 里填了测试数据再切到 B，B 的输入框是空的（不会把 A 的数字喂给 B 的程序），
> 切回 A 时你填过的还在。
>
> **同样一份代码连按 F9 是"秒出"**：运行前会按源码内容（+编译器+编译选项）查缓存，
> 内容没变就直接用上次编好的 exe，不再重新编译；改了代码自然就重新编译。
> 这样"看一遍输出、改一行、再看"的节奏不会被每次 0.1~0.5 秒的编译打断。

#### 为什么不再开系统命令行窗口

早先 F9 会另开一个真正的控制台，好处是 `scanf` 能现场交互；实测下来代价更大：

- 屏幕上突然多一个黑框，学生以为是**卡住 / 中毒 / 报错**，先去关掉；
- 黑框和面板两处都有输出，讲解里引用行号时**对不上**；
- 面板里拿不到退出码、用时、超时这些信息，出错时没法引导学生回去按 F5。

所以现在统一在面板里跑：输出、用时、退出码、超时提示都在同一页。
需要输入时既可以在运行前填好一次性给它，也可以**运行中回车逐行回答**（半交互）——
对初学者的练习题足够，而且**看得见"输入了什么、得到什么"**。

> 代码区和下方面板之间的**分割条抓握区做了加宽**（30px，约一个半鼠标箭头的高度）。
> 原来的 4px 细线基本只能靠"猜"去命中，尤其下方面板停在「运行输出」时，
> 那条线紧贴着输入框上沿，鼠标来回找交界点很难受。现在整条浅灰带都能按住拖，
> 悬停会加深提示。

> **程序输出要按编译器的字符集解码**（实测差异）：
> MSVC 不带 `/utf-8` 时，字符串字面量按**系统 ANSI 代码页**（中文 Windows 上是 GBK）生成；
> 而 MinGW GCC 默认按 **UTF-8**。同一份 UTF-8 源码，两家输出字节不同，
> 解码时选错代码页，中文输出就全是乱码。

#### 运行学生代码一定会遇到的情况

| 情况 | 处理 |
|---|---|
| **死循环**（`while(1)`、忘写 `i++`） | 面板模式下**只按"程序真在跑"的时间计时**，超时后连子进程树一起杀（`taskkill /F /T`）；等输入的时间不算，所以不会误杀"正在等人敲键盘"的程序。超时秒数可调（默认 10 秒），也可以点「停止」立刻终止 |
| **程序在等输入，看起来像卡住** | 运行中超过 2.5 秒没有新输出时，面板会主动提示"可能在等 scanf"；输入后回车即可，**等多久都不会超时** |
| **程序等输入**（`scanf`） | 半交互：程序运行中在输入框回车逐行喂（不弹黑框）；也可以运行前填好一次性给。**等输入的时间不计入超时** |
| **输出刷屏** | 面板模式输出限长 200KB，超出提示已截断 |
| **程序崩溃** | Windows 只给一个巨大返回码，翻译成人话（见下） |
| **中文乱码** | 控制台按编译器选代码页；面板模式按 UTF-8 优先解码 |
| **上次的窗口还开着** | **每次运行用独立工作目录**（见下） |

**返回码翻译**——学生看到 `3221225477` 等于什么都没看到：

| 返回码 | 说给学生的话 |
|---|---|
| `0xC0000005` | 读写了不该访问的内存，最常见是**数组越界**或**空指针** |
| `0xC0000094` | **整数除以 0**，检查 `a % b` 里的 b |
| `0xC00000FD` | **栈溢出**，多半是递归没有终止条件 |
| `0xC0000409` | 栈缓冲区被破坏，常见于越界写数组 |

> **三个实测踩出来的坑**
>
> 1. **BOM 会污染 stdin**：源码是 UTF-8 带 BOM 时，如果拿 `utf-8-sig` 去编码要喂给程序的输入，
>    stdin 开头就多了 `EF BB BF` 三个字节，`scanf("%d")` 直接解析失败——程序拿到未初始化的
>    垃圾值，而界面上完全看不出哪里错了。BOM 是文件层面的东西，喂 stdin 时不该带。
> 2. **解码顺序不能"谁先成功用谁"**：GBK 的字节空间很宽，几乎任何字节都能解出**某个**结果，
>    所以"GBK 解成功"不是证据；UTF-8 校验严得多，GBK 中文串几乎不可能碰巧合法。
>    必须先严格试 UTF-8。实测按源码编码优先时，程序输出的中文会变成 `תȦ` 这样的乱码。
> 3. **每次运行要有独立的工作目录**（这条最坑，也是最像"运行功能坏了"的原因）：
>    上一次的程序还没跑完时，它锁着 `a.exe`，下一次编译写不进去就失败，
>    而界面只会说**"编译没有通过"**——完全看不出真正原因是"上一次的运行还没结束"。
>    表现是"有时候能运行，有时候莫名其妙不能运行"。
>    现在每次运行都拿一个独立目录（`unique_workdir`，命名带**进程内递增序号**——
>    只用时间戳的话，学生连点两下会撞在同一毫秒上，等于没隔离）。

### 新建文件

![新建文件](docs/screenshots/panel_newproj.png)

`Ctrl+N` 或工具栏「新建文件」：填文件名、选存放位置、选起始内容，
然后得到一个 `.c` 文件并直接在编辑器里打开。

- 默认存放位置是 `文档\ctutor项目`，改过之后会记住（`文件 → 设置项目存放位置…`）
- 内置 4 个模板：空白 / Hello World / 读入两个数求和（含 `scanf`）/ 带循环和数组
- 文件名会校验（非法字符、以点或空格结尾等），重名**不会静默覆盖**，先问一句
- 输入 `作业1.c` 不会变成 `作业1.c.c`——后缀由程序统一补

**扁平存放，不套文件夹。** 早期版本会建一个同名文件夹再往里面放 `main.c`：

```
改之前： ctutor项目 / 第一次作业 / main.c      ← 要进两层才找到
现在  ： ctutor项目 / 第一次作业.c             ← 一眼看到
```

学生只需要一个 `.c` 文件。多一层文件夹意味着交作业要再点进去一次、
发微信要拖对文件、老师收上来是一堆同名 `main.c`——没有任何好处。

### 关掉也不会丢（上次进度）

关程序时会把当前状态记下来，下次打开**直接接着写**：

- 上次开了哪几个文件、各自用什么编码
- 当前停在哪个标签
- **还没保存的改动内容**——这一条最关键。只记文件名的话，写了一半忘了存，
  下次打开文件里还是旧的，那段代码等于白写

恢复出来的未保存内容**标签上依然带 `*` 号**，不会让你误以为已经存盘了。

几条稳妥性设计：

| 情况 | 处理 |
|---|---|
| 文件没改过 | 只记路径，下次**从磁盘重读**（文件被别的程序改过也能拿到最新的） |
| 文件被删了 / 挪走了 | 跳过它，程序照常打开，不报错 |
| 会话文件坏了 / 格式不对 | 当作"没有上次进度"，退回示例代码，**绝不因此打不开程序** |
| 从没保存过的新文档 | 内容只在会话里，照样能恢复 |

会话文件存在 `%APPDATA%\ctutor\session.json`，**不放项目目录**——
把项目文件夹打包发给别人时不会带上你的编辑状态。写入用"先写临时文件再替换"，
中途断电不会留下半个 JSON。


### 同时开多个文件

![多标签](docs/screenshots/panel_tabs.png)

学生经常是「第 1 题还没弄明白，第 2 题又要交了」。所以打开或新建的文件都进标签栏：

- 点标签切换，点 × 关闭（`Ctrl+W`），标签可以拖动排序
- **各标签互不干扰**：内容、光标、编码、上一轮的标红都各自保存
- 已经打开过的文件再打开会**跳过去**，不会开出两份来改乱
- 标签标题带 `*` 表示有未保存改动，路径栏也会写 `● 未保存`

### 关掉之前一定先问一句

初学者最容易丢东西的一步：写了一半直接点右上角 X。

所以**关标签**和**退出程序**时，只要那个文件有未保存改动，都会先弹一句
「保存 / 不保存 / 取消」。选「取消」就什么都不做，回到编辑状态。

> 同时开了 4 个文件、每个都改过的时候，以前是**连弹 4 个框**——中间手一抖点了
> 「取消」，整个关闭就被中止，用户以为程序卡住了，往往直接强制结束进程，
> **那才会真的丢东西**。现在合并成一次询问：一次列出所有未保存的文件，
> 给「全部保存 / 全部不保存 / 取消」。
>
> 而且顺序改成了**先把会话写下去、再弹询问框**。哪怕最后点了取消、
> 或者进程被强制结束，「上次进度」也是完整的，下次打开所有文件都还在。

> 这里有个反直觉的实现细节：判断"有没有改过"用的是**和上次保存的内容逐字比对**，
> 而不是监听编辑器的内容变化事件——因为切标签时也会触发那个事件，
> 结果每次切换都被判成"已修改"，退出时白问一遍。
> 另外 Monaco 会把 `\n` 归一成 `\r\n` 返回，不统一换行符的话同样是"一打开就算改过"。
> 两个坑都有对应的测试守着。

### AI 修改：让模型给一份能编译的代码

![多标签](docs/screenshots/panel_tabs.png)

工具栏「AI 修改」（`Ctrl+Shift+A`）会先问你**想怎么看改了什么**，三种方式：

| 方式 | 原文件 | 适合 |
|---|---|---|
| **原位修改** | 直接改进编辑器，标签带 `*` | 想马上看到结果，改完点「对照」比一比 |
| **独立窗口** | **一个字都不动** | 想两个窗口并排看，边看边自己改 |
| **行内注释** | **一个字都不动** | 只想看提示，自己动手改 |

「对照」按钮（`Ctrl+Shift+D`）会把修改前后逐行对比：绿色是新增、红色是删掉的。

**边界是刻意守住的**：

- **永远不写文件**——只改编辑器缓冲区，存不存由你决定
- **不会自动保存**，标签会变成未保存状态，退出时会问
- **随时可还原**：`Ctrl+Shift+Z` 一步回到修改前
- **模型偷懒会被拦住**：它很爱说"其余部分不变"或者只返回改动的几行。
  把这种半截代码粘回去，本来能编译的程序反而会废掉，所以有一道校验
  （长度、`...` 省略、和原文的比例），不像完整文件就**直接拒绝**而不是硬塞
- **模型说没把握就不给代码**，只给建议

> 这个功能和「讲解」是分开的两条线：讲解按设计**绝不输出可复制代码**，
> 修改则是一条显式触发的通道，必须点按钮才发生。

### 使用说明是独立窗口

按 `F1` 或点菜单「帮助 → 使用说明」会打开一个独立窗口，**再点一下就关掉**。

- 说明不再挤进讲解栏，看说明时刚才的讲解还在
- 说明窗口开着也可以照常检查、运行，互不干扰
- **第一次使用会自动弹出一次**，之后不再打扰（记在用户配置里）

> 之前是"说明和讲解抢同一块地方"：看说明时看不到讲解，按检查又要自动收起说明，
> 用户会以为"按了没反应"。搬到独立窗口后两个问题一起消失。

> 顺带修掉一个自己挖的坑：首次自动弹出原本用的是 `toggle_help`（切换），
> 如果用户恰好在那一瞬间自己点开了说明，定时器一到反而**把它关掉**。
> 现在拆成 `show_help`（只开）和 `toggle_help`（开/关）。

### 右键菜单是中文的

编辑器里右键弹出的是**全中文菜单**：剪切 / 复制 / 粘贴 / 删除 / 全选 /
添加锚点… / 锚点列表… / 删除本行锚点 / 撤销 / 重做，右侧带 `Ctrl+X` 这类快捷键提示。
按 Esc 或点别处关闭。

**为什么自己做，而不是翻译**：这个 qtmonaco 带的 `monaco-core.js` 里没有右键菜单
那部分贡献——派发 `contextmenu` 之后 DOM 里始终没有菜单，右键请求落到 Qt 上，
弹出来的是 WebEngine 自己的英文原生菜单，网页改不了它的文字。

所以做法是**接管**：页面里对编辑器区域的 `contextmenu` 调 `preventDefault()`，
原生菜单不再弹；同时画一个自己的菜单。每条命令都真的能用——复制/粘贴走系统
剪贴板，全选选中整篇，撤销/重做走编辑器核心命令。

### 锚点（书签）

给一段代码打个记号，回头一眼能找到：

- **添加**：编辑器里右键 → 添加锚点…，默认用当前行的代码起名，可以改成
  「主循环」这种好认的名字
- **显示**：锚点贴在**编辑器最右端**，是一条写着名字的蓝色标签；点一下光标直接
  跳到那一行并居中
- **管理**：工具栏「锚点」（或右键 → 锚点列表…）列出全部锚点，双击跳转；
  同一行再加一次＝改名，不会叠成两条；右键 → 删除本行锚点可以删掉
- **跟着走**：滚动、缩放、改窗口都跟着动；编辑代码后锚点跟着原来那一行走；
  滚出视野自动隐藏
- **零影响**：不往 `.c` 里插字符、不加注释、不标「已修改」，只存在
  `%APPDATA%\ctutor\session.json`，发给别人也看不到

### 一键对齐（整理缩进）

初学者写完一屏代码，缩进常常是花一块平一块的——**报错位置反而更难找**，
因为你看不出哪个 `}` 对应哪个 `{`。

工具栏「对齐」（`Ctrl+Shift+F`）：按大括号层级把每行缩进重新排一遍。

**它只动空白。** 这是硬约束，不是口号：

| 会改 | 不会改 |
|---|---|
| 行首缩进 | 任何非空白字符 |
| 行尾多余空格 | 行的顺序、行的数量 |
| 空行里残留的空格 | 有没有换行 |

实现上有一道保险：格式化后把前后两段文本的**所有空白抹掉**再比对，
只要有一个字符不同就**放弃本次对齐、返回原文**。宁可不变，也不能改坏。

几个刻意保留不动的地方：

- **字符串里的括号不算块**：`printf("{")` 不会让后面整片缩进错位
- **多行字符串内部的缩进原样保留**——这是唯一一处"改缩进就等于改内容"，
  动它就是改你程序输出的东西
- **块注释里的画框不动**（很多人用 `/* +---+ */` 画表格）
- **续行不动**：`printf("%d %d\n",` 换行后那几个参数，按你原来的对齐保留

> 为什么不用现成的格式化工具？因为 C 的格式化器普遍会**重排 token、拆行合并行**，
> 一旦哪里有它不认识的写法，就可能产出编译不过的代码。
> 对"给初学者看报错"这个目标来说，**只动空白**是收益最高、风险最低的选择。
>
> 对完发现不对？`Ctrl+Shift+Z` 一步撤回（Monaco 的 `set_text` 会清空它自己的撤销栈，
> 所以这里自己记了一份原文）。

### Ctrl + 滚轮 / Ctrl + 加减号缩放

| 操作 | 效果 |
|---|---|
| `Ctrl` + `=` 或 `Ctrl` + `+` | 放大 |
| `Ctrl` + `-` | 缩小 |
| `Ctrl` + `0` | 恢复默认字号 |
| `Ctrl` + 滚轮 | 在编辑器、讲解区、运行输出区都能缩放 |

缩放档位会写进用户配置，下次打开还是这个字号。

> **两个坑，第一个是"快捷键完全不生效"的根因**
>
> 1. **`QKeySequence.ZoomIn` 不是按键序列，是 `StandardKey` 枚举（值 16）。**
>    写 `act.setShortcut(QKeySequence.ZoomIn)`，PySide6 会把它当成"按键码 16"，
>    注册成 `QKeySequence(16)` —— 也就是控制字符 `'\x10'`，**快捷键静默失效**：
>    不报错、不提示，就是按了没反应。
>    同一个错误我还在 `Ctrl+O`（`QKeySequence.Open`）和 `Ctrl+S`（`QKeySequence.Save`）
>    上犯过，那两个也一直是坏的。现在一律写成 `"Ctrl+O"` 这样的显式字符串。
>    （也别指望 `QKeySequence.keyBindings(...)` 来取标准绑定——实测这个 PySide6
>    构建调用它会直接**段错误**，退出码 `0xC0000005`。）
> 2. **不能只靠 `QAction` 的快捷键。** Monaco 是内嵌的 Chromium，
>    Qt 派发按键前会先发 `ShortcutOverride`，焦点控件接受它快捷键就整个不触发。
>    所以缩放改由**挂在 `QApplication` 上的事件过滤器**接管——
>    它在事件送达焦点控件之前就能看到，绕开了这个问题，也顺带摆脱了
>    "窗口必须活跃"的前提（这一点还让快捷键**可以被自动化测试验证**）。

`QTextBrowser` 的 `zoomIn/zoomOut` 是**累加**的，所以代码里记录"已经应用了多少档"、
每次只做差值——否则来回缩放几次后状态漂移，Ctrl+0 就回不到默认了。

Monaco 那边同时保留了 `mouseWheelZoom`（作为万一过滤器没拿到事件时的兜底）；
正常路径下事件已被过滤器消费，不会双重缩放。

### 出错位置标红

只在下方给个行号，学生还得自己数行——所以直接把错误画在代码上（`engine/editorui.py`）。

| 对象 | 表现 |
|---|---|
| **正在讲的那一条** | 整行深红底 + 左侧红边 + 行号区**红点** + 具体 token 红色下划线 |
| 其它错误 | 整行淡红底 + 行号区**橙点**（让他知道"别处还有问题"，但不抢注意力） |
| 警告 | 默认不标，否则页面花花绿绿反而看不清重点 |
| 滚动条 | 右侧 overview ruler 同步打点，滚动到别处也知道哪几行有问题 |

编译通过时标红自动清空；打开另一个文件时也会清掉上一次的。

两个实现上的注意点：

1. **选中的那一条必须无条件标出来**，哪怕它是警告。否则会出现很别扭的情况：
   正在讲的是一句 `unused variable` 警告、页面上另有错误，结果别的行标红了、
   正在讲的那一行反而没标 —— 高亮和讲解对不上。（这是写测试时抓出来的真 bug）
2. **`runJavaScript(js, None)` 不合法**：PySide6 的 `runJavaScript` 有两个重载，
   显式传 `None` 当回调会让调用整个失效——表现为"代码看着没问题，标红就是不出现"。
   所以要么不传第二个参数，要么传真正的回调。

降级编辑器（Monaco 加载失败时用的 `QPlainTextEdit`）用 `setExtraSelections` 实现同样的效果，
避免这个功能在某些机器上直接消失。

两条设计约束：

1. **绝不修改学生原文件**——检查时把编辑区内容写到 `build/panel/` 的工作副本，
   编译的是副本；只有显式按「保存」才写回原文件。
2. **界面与命令行共用同一条引擎路径**（`engine.report.check_once`）与同一份分层数据，
   因此不会出现"命令行说 A、面板说 B"的分裂（有测试断言两者层结构完全一致）。

> **实测坑**：Qt 在找不到字族时会**静默把所有中文画成方块**。实测离屏渲染时
> `QFontDatabase.families()` 返回 0 个字体，整个界面全是 □。因此 `ensure_cjk_font()`
> 显式加载 Windows 自带中文字体（微软雅黑 → 黑体 → 宋体），且在 `MainWindow` 构造时就加载，
> 任何入口（测试、探针、被别的程序 import）都不会漏掉。

## 代码补全（减少打字与拼写错误）

输入前几个字母就会弹出候选，例如打 `pri` 选 `printf`、打 `for` 直接补出完整循环。

**词条是可编辑的数据文件**：`data/completion.json`（65 条，教师可自行增删）。
构成：12 个代码片段 + 25 个关键字 + 26 个标准库函数 + 2 个常量。

补全不只是省打字，**片段本身就是示范**——这是刻意的教学设计：

| 片段 | 内建的"正确范式" |
|---|---|
| `scanf` | 带 `&`（漏 `&` 是初学者最常见的运行时崩溃原因） |
| `for` | 两个分号 + 花括号（不会写成逗号，也不会漏花括号） |
| `if` / `else` | 完整的配对结构（避免 if 后误加分号导致 else 悬空） |
| `main` | 标准 `int main(void)` 写法 |
| `swap` | 借助第三个变量（不会写出互相覆盖的错误交换） |
| `include` | 下拉可选 stdio.h / stdlib.h / string.h / math.h |

每条都有中文说明，鼠标悬停能看到"这是什么、容易错在哪"。

> **实现说明**：qtmonaco 打包的 JS 只为 `python` 硬编码注册了补全提供者，而且
> `globalAPI: false`（`window.monaco` 不存在）。这里通过**子类覆盖
> `Monaco._load_editor()` 注入自己的模块脚本**来实现——不修改第三方包，
> 升级依赖不会被覆盖。注入脚本里 `import('./assets/monaco-core.js')` 拿到的
> 导出中 `r` / `m` 即完整的 monaco 命名空间（压缩后名字，实测得出）。
>
> 另一个实测坑：`runJavaScript` 的执行上下文 base URL 是 `about:blank`，
> **在 Python 侧无法 `import()`**；因此必须由页面内脚本把 `monaco` 句柄挂到 `window` 上，
> 外部才能用它做自检。

## 如何接入 AI

AI 是**可选增强**，不配也能用——本地知识库命中时本来就不联网、不需要密钥。

### 三步启用

1. 拿到 DeepSeek API Key（[platform.deepseek.com](https://platform.deepseek.com) 创建，`sk-` 开头）
2. 用下面任一种方式配置：

   | 方式 | 操作 | 适合 |
   |---|---|---|
   | **面板菜单**（推荐） | 打开面板 → 菜单 **AI → 设置 DeepSeek 密钥…** → 粘贴 → 确定（会自动测一次连接） | 所有人 |
   | 命令行 | `python cli.py set-key`（输入时不回显） | 习惯终端 |
   | 环境变量 | `set DEEPSEEK_API_KEY=sk-xxxx` | 临时试用、CI |

3. 面板里勾上 **「AI 补充」**（勾选状态会记住）

### 密钥存在哪里

写到 **`%APPDATA%\ctutor\config.json`**，而不是项目目录。这样：

- 把项目文件夹打包分享/开源时**不会把密钥带出去**；
- 项目移动位置后密钥仍然有效；
- 项目内的 `config/ctutor.json` 也被 `.gitignore` 忽略，双保险。

优先级：**环境变量 > 用户配置 > 项目配置**（环境变量最高，便于临时覆盖）。

> 如果你的 DSH 里已经配过 DeepSeek，可以直接导入，无需手动复制：
> ```bash
> python tools/import_key_from_dsh.py --dry-run   # 先看会导入什么
> python tools/import_key_from_dsh.py             # 导入并测连通
> ```
> 凭据跨应用搬运**由你显式触发**，工具不会自动做。脚本全程只显示打码后的密钥。

### 什么时候会调用、花多少钱

只在**本地知识库没有收录**这个错误码时才调用一次。命中时零成本零延迟。

实测（当时用的模型是 deepseek-flash，现默认 deepseek-chat）：单次解释 `tokens in=718 out=248`，其中 **512 个 token 命中上下文缓存**，
成本约 **0.0015 元**；缓存命中价 $0.003/M 与未命中 $0.15/M 相差 50 倍，
所以系统提示被刻意做成字节稳定的前缀（有测试断言其 sha256 不随输入变化）。

### 安全与质量上的约束（都有测试）

- 发送前**脱敏**本机路径、邮箱、疑似密钥
- **位置只来自编译器**——模型返回的任何行号/文件名一律丢弃
- 模型输出必须通过 JSON schema 校验；失败重试一次，再失败**降级为只给定位**
- 输出完全不是 JSON 时**失败关闭**，不展示未经校验的自由文本
- **答案泄漏守卫**：剥离完整可复制的代码解法（文献实测模型 48% 会违规）
- 所有界面/日志里只出现**打码**后的密钥

```
c-tutor/
  cli.py              入口
  engine/             源码
  data/
    kb/msvc.json      中文知识库（唯一长期增值的资产）
    kb/gcc.json
    top_errors.json   Top-20 高频清单（有来源依据，见下）
  config/
    ctutor.example.json   示例；复制为 ctutor.json 后生效（已被 .gitignore 忽略）
  bin/                放便携工具链（如 w64devkit），见 bin/README.md
  log/                运行时生成：ctutor.jsonl / unmatched.jsonl
  build/              编译产物
  tests/              5 个测试套件
```

所有路径都相对工具根目录解析。编译器路径、编码、超时、输出上限、AI 参数全部走
`config/ctutor.json` 或环境变量（`CTUTOR_GCC` / `CTUTOR_VCVARS` / `CTUTOR_STD` / `CTUTOR_COMPILER`），
**代码里不硬编码**。

## 三步开发的内容

**第一步 本地报错解释器**：编译 → SARIF 解析 → 中文知识库匹配 → 本地讲解，完全不联网。

**第二步 分层讲解**：一条诊断讲成 5 层（结论／定位／原因／改法／知识点），`--depth 1..5` 渐进披露。
默认 4 层——本工具的本职就是给出明确的修改意见。

**第三步 接入 DeepSeek**：只在本地知识库未命中时调用；稳定前缀吃上下文缓存；JSON 校验 +
重试 + 降级；答案泄漏守卫；位置锚定；发送前脱敏。

## 实测发现的两个中文专属陷阱（英文环境永远遇不到）

这两个都是**只在中日韩源码上出现**的问题，纯英文测试完全测不出来。

### 1. MSVC 的列号模型：ASCII 宽 1，双字节字符宽 3

受控实验（0~4 个汉字）结果：

| 汉字数 | 字符列 | 字节列(GBK) | MSVC 列 |
|---|---|---|---|
| 0 | 16 | 16 | 16 |
| 1 | 17 | 18 | 19 |
| 2 | 18 | 20 | 22 |
| 4 | 20 | 24 | 28 |

即 `列 = 字符列 + 2 × 之前出现的双字节字符数`。纯 ASCII 行两种模型一致，
所以**按字符列直接画插入符，每遇一个汉字就会偏 2 列**。已修（`encoding.col_to_char_index`），
并有端到端回归测试：0~4 个汉字行的插入符都必须落在 `int x` 上。

GCC 侧我们传了 `-fdiagnostics-column-unit=byte`，列号是字节偏移，走另一条换算路径。

### 2. MSVC 的 SARIF 会含被截断的多字节字符

SARIF 里带一个 `snippet` 字段，装着源码行的**按字节截断**片段。源码含中文时截断点可能
落在多字节字符中间：

```json
"text": "    int x = 10\xef\xbc"     ← 三字节的「；」被切掉最后一字节
```

于是**整份 SARIF 不是合法 UTF-8**，严格解码直接失败。已修：容错解码（结构完好，
只有那半个字符降级为 U+FFFD），并有回归测试确认错误码与行号依然正确。

## 知识库是怎么长起来的

第一版 27 + 25 条是按调研方案手工写的。之后分两轮扩充到 61 + 53 条，
**每一轮的来源都不同，可信度也不同**：

| 轮次 | 来源 | 可靠性 |
|---|---|---|
| 第一版 | 调研方案（c-error-helper 等开源规则）+ 人工撰写 | 中 |
| 第二轮 | `tools/probe_snippets.py` 对 **MSVC 14.51 / GCC 16.2 的真实编译实测** | **高**（码是编译器自己报的） |
| 第三轮 | 三个并行调研：英文社区高频清单、中文社区与中国高校材料、开源知识库审计 | 参考（需实测确认） |

**经验教训：网上抄的错误码经常对不上。** 调研报告里说"全角空格报 C3872"，
我实测得到的是 **C2065**（因为编码和上下文不同）。所以现在的规矩是：
**写进知识库的每个码，先用 `tools/probe_snippets.py` 实测确认。**

### 调研里最值得记的三条

1. **"烫烫烫"不是隐式类型转换。** 中文社区有篇文章的摘要这么写（错的），
   真因是：缺 `\0` + VS Debug 用 `0xCC` 填充栈 + GB2312 把 `0xCCCC` 显示成"烫"。
   有意思的是**同一篇正文解释是对的**——"摘要错、正文对"正是 RAG 类工具最容易踩的坑。
2. **"无脑把 scanf 换成 scanf_s"是社区流行建议的恶果。**
   `%c` 必须额外传长度参数（`scanf_s("%c", &c, 1)`），大量教程只教"加个 `_s`"，
   结果学生换完崩得更厉害。
3. **教材用 `gets()` 必然编译不过。** 微软 C3861 官方文档的示例**直接就是 `gets()`**——
   这从编译器侧官方证实了"老教材代码在新 VS 上报错"不是学生抄错了。

### 中文特有问题单独处理

这些是英文项目结构上覆盖不到的，也是本项目存在的理由：

- **全角标点**（U+FF1B 等）：MSVC 说"数字上的错误后缀"、GCC 16 说 `invalid suffix '；'`
- **全角空格 / 不间断空格 / 零宽字符**：**最坑的一类**——报出来是
  `C2065 "x": 未声明的标识符`，看起来像拼写错误。本工具会：
  - 直接指出"这一行里有看不见的字符"，并给出列号
  - 当报错消息里的名字是**乱码**（`鈥渉i鈥`、`int聽a`）时，
    额外提示"问题不在拼写，在字符/编码"——因为按拼写方向查永远查不出来
- **编码错位**：C4819 / GCC 的 `stray` 系列

### 错误雪崩：一次报几十条不代表错了几十处

编译器经常一次喷几十条错误，但它们绝大多数是**第一条的连锁反应**。
本工具只讲第一条，并且在错误数 ≥3 时明确提示：

> 一次报很多条通常**不是很多个错误**——第一条往往是根因，
> 修好它之后后面那些多半会一起消失。先只改下面讲的那一处，再重新检查。

### 选哪一条讲：一个被测试逼出来的修正

规则是"有错误取第一条；只有警告时挑最值得讲的"。第二条最初写成
"挑**本地知识库能解释**的那条"——在知识库还小的时候**碰巧**能用，
因为噪音条目还没被收录、会被自动跳过。

知识库一大，`unused variable` 也被收录了，它立刻抢走了讲解位置：
学生问"函数为什么报错"，得到的是"变量 s 没用到"。

**修正：把"没用到"这类噪音警告排到后面，先按"这条警告像不像真缺陷"排序。**

> 教训：**"我们能解释"和"这条值得讲"是两件事，不能用前者代替后者。**

真实 API 实测（当时用 deepseek-flash，现默认 deepseek-chat）：未收录错误由 AI 补齐三层讲解，位置仍来自编译器；
`tokens in=718 out=278，上下文缓存：命中 512 / 未命中 206`；单次约 **$0.0002**。
知识库命中时**完全不调用模型**。

## 两个编译器后端的实测差异

GCC 与 MSVC 对同一个错误的报法完全不同，本项目两个后端都已用真实编译器验证过
（GCC 16.2.0 / w64devkit、MSVC 14.51）。代表性的差异：

| 场景 | MSVC | GCC |
|---|---|---|
| 漏分号 | `C2146 缺少";"` | `expected ',' or ';' before 'printf'`（**无错误码**） |
| 全角分号（GBK 源码） | `C2059 语法错误:"数字上的错误后缀"` | `stray '\243' in program` |
| 漏 `#include` | `C4013`（**仅警告**，程序照跑） | `-Wimplicit-function-declaration`（**错误**） |
| `main` 拼错 | `LNK1561`（文本，不进 SARIF） | `undefined reference to 'main'`（文本，无行号） |
| 变长数组 `int a[n]` | `C2133/C2057` **报错** | **合法，无诊断** |
| `scanf` 漏 `&` | `C4477` + `C4700`（警告） | `-Wformat` + `-Wuninitialized`（警告） |

> 倒数第二行值得单独说：**同一份代码在 GCC 上能跑、在 MSVC 上报错**——
> 这正是学生"在我电脑上没问题，交上去编译不过"的典型来源。
> 样本集里刻意保留了它作为对照。
>
> GCC 侧还有一个实测坑：诊断没有关联警告选项时，它会把 SARIF 的 `ruleId`
> 写成级别本身（`"error"`），而不是规则标识符；部分警告还会带一个多余的尾随等号
> （`-Wformat=`）。两者都已在解析层归一化。
