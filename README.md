# ctutor — C 语言报错解释器

**把 C 编译器那句看不懂的报错，翻译成中文人话。**

面向中文初学者的 C 语言报错解释工具。**本地知识库优先，AI 只兜底**——
知识库命中时完全不联网、不花钱。

![出错位置标红](docs/screenshots/panel_marks.png)

## 它解决什么问题

初学者最常见的困境不是"不会写"，而是**编译不过却看不懂为什么**：

```
error C2146: 语法错误: 缺少“;”(在标识符“printf”的前面)
```

- 报的是第 5 行，可问题在第 4 行末尾
- 即使找到了，"缺少分号"这四个字也没告诉他**为什么**必须加
- 一次报 30 条，不知道从哪下手

ctutor 的做法：**只讲最可能相关的那一条**，分 5 层讲清楚
（结论 → 定位 → 原因 → 改法 → 知识点），并且把出错的行**直接在编辑器里标红**。

## 几个和同类工具不一样的地方

| | |
|---|---|
| **本地知识库优先** | 61 条 MSVC + 53 条 GCC 中文解释，人工撰写。**命中时零成本、零延迟、零幻觉**，不联网 |
| **位置只信编译器** | 行号/列号永远来自编译器，模型返回的一律丢弃——模型只负责"怎么说人话" |
| **不替你改代码** | `check` 永远不修改你的文件；检查的是工作副本。`fix` 是需要显式调用的实验性子命令 |
| **中文特有坑** | 全角标点、全角空格、Word 复制带出的不间断空格——这些报错**看起来像拼写错误**，本工具会指出真正原因 |
| **真的能运行** | F9 开系统命令行窗口，`scanf` 可以真正交互输入；死循环会超时终止；崩溃返回码翻译成人话 |

## 安装与快速开始

**要求**：Python 3.9+；需要一个 C 编译器（Windows 上装 Visual Studio，或把
[w64devkit](https://github.com/skeeto/w64devkit) 解压到 `bin/gcc/`，见 [bin/README.md](bin/README.md)）。

```bash
git clone https://github.com/<你的用户名>/ctutor.git
cd ctutor

# 命令行：零第三方依赖，现在就能用
python cli.py doctor                  # 环境自检：找编译器、看配置
python cli.py check 你的代码.c         # 分层讲解报错
python cli.py run 你的代码.c --input "3 4"   # 编译并运行

# 图形面板：需要 PySide6 + qtmonaco
pip install -i https://pypi.tuna.tsinghua.edu.cn/simple PySide6 qtmonaco
python panel.py
```

> 国内直连 PyPI 实测只有约 0.6 MB/min，所以上面用了清华镜像。

面板里：**F5** 检查、**F9** 在系统命令行里运行、**Shift+F9** 在面板内运行、
**Ctrl+N** 新建项目、**F1** 使用说明、**Ctrl + 滚轮**缩放。

AI 是可选增强，不配也能用：见下方「如何接入 AI」。
**密钥存在用户目录**（`%APPDATA%\ctutor\config.json`），不在项目里，不会被误提交。

## 定位与边界

> **只解决「编译不过、看不懂」，不解决算法、调试、考试。**

凡是帮人读懂报错的功能保留；凡是替人改代码的功能一律不是主路径。

## 打包分发给别人

把整个程序打成"解压即用"的便携包（对方不用装 Python，也不用装编译器）：

```bash
python tools/build_package.py                # 完整打包（含便携编译器）
python tools/build_package.py --no-toolchain # 不捆绑编译器（体积小很多）
python tools/build_package.py --skip-build   # 跳过 PyInstaller，只重组目录
```

产物在 `_pack/` 下，**解压后双击 `ctutor.exe` 即可**——
不需要装 Python，不需要装编译器，不需要管理员权限，不写注册表。

| 项 | 说明 |
|---|---|
| 入口 | 打包时以 `main.py` 为入口：不带参数开图形面板，带子命令走命令行 |
| 程序根目录 | 冻结后 `config.ROOT` 取 **exe 所在目录**，而不是 PyInstaller 的临时解压目录——否则 `log/`、`build/` 会写进临时目录，程序一关就没了 |
| 自带编译器 | 捆绑 [w64devkit](https://github.com/skeeto/w64devkit)（便携 GCC），对方机器上没编译器也能用 |
| 体积 | w64devkit 解压后 708MB，脚本会砍掉对纯 C 教学无用的部分（32 位运行时、CMake、C++/Fortran 前端、gdb、文档），砍到约 360MB |
| 自动验证 | 打包完会**运行打包出来的 exe 做离屏自检**：能否启动、Monaco 是否加载、能否真编译一个样本、讲解是否命中。任一不通过就明确报错，不会让你把坏的包发出去 |

> **打包踩到的坑（都已在代码里处理）**
>
> 1. **Windows 的 260 字符路径上限**（真实事故：朋友从微信下载目录直接运行，报
>    `Failed to load Python DLL ... LoadLibrary: 找不到指定的模块`）。
>    根因是包内最深路径 +145 字符，加上对方的目录前缀达到 303 字符 ——
>    **超出上限后 Windows 自带解压器会静默跳过文件**，解压出来的包本身就已经是残的。
>    处理：删掉 C++ 头文件（那条最深的链，纯 C 教学用不到）、`bin\w64devkit` 改名
>    `bin\gcc`，最深降到 +79；包名与目录名改成纯 ASCII；
>    并在包里放一个**不依赖 exe 的自救脚本** `检查是否路径太长.bat`（exe 起不来时它还能跑）。
>    实测：在 152 字符的深目录下解压完整（4000 个文件）且运行正常。
> 2. **qtmonaco 会启动 Python LSP 服务**：它在构造编辑器时执行 `sys.executable -m pylsp`。
>    打包后 `sys.executable` 就是本程序自己——会变成"启动自己"。已在 `panel.py` 里覆盖
>    `get_pylsp_host` 拦掉，并在 spec 里排除整套 LSP 依赖（顺带省掉几十 MB）。
> 3. **`pythonw` / windowed exe 下 `sys.stdout` 是 `None`**：直接 `print` 或
>    `sys.stdout.reconfigure` 都会崩，而且**异常是静默的**（双击没反应）。已加防护 +
>    崩溃日志 + 自检结果写 JSON 文件（无控制台也能做自动化验证）。
> 4. **GCC 需要可写的临时目录**：受限环境下 gcc 会直接失败并输出
>    `Cannot create temporary file in ...: Permission denied`，表现为"一条诊断都没有"。
>    已把 `TMP/TEMP/TMPDIR` 指到工作目录下。
>
> **验证这类问题的方法论**：一开始我用**目录联结**去模拟长路径，结果两次"复现"都
> 不可靠（联结是重解析点，行为和真实目录不同）。改用**真解压**之后才看清真相：
> 解压日志里成百条 `ExtractToFile: Could not find a part of the path ...`，
> 直接指向"解压器静默跳过超长路径文件"这个根因。

### 扩充知识库

新增条目一律**先实测再写**，不照抄网上的错误码（版本不同、码会变）：

```bash
# 1) 用真实编译器验证某个错误到底报什么码、什么消息
python tools/probe_snippets.py --compiler msvc --only 全角
python tools/probe_snippets.py --only 指针        # 两个编译器都跑

# 2) 按实测结果撰写条目，追加进 tools/expand_kb.py 后合并（幂等，可重复运行）
python tools/expand_kb.py
```

`tools/expand_kb.py` 是幂等的：已存在的条目会跳过；要修改已存在的条目必须用
`PATCHES`（**只改脚本里的定义不会生效**——合并时整条跳过，这个坑踩过）。

### 一键运行

![运行输出](docs/screenshots/panel_full_run.png)

**两种方式，默认走系统命令行**：

| 快捷键 | 方式 | 适合 |
|---|---|---|
| **F9** | **系统命令行窗口**（真正的控制台） | 默认。`scanf` 能真正交互输入，和书上的行为一致 |
| **Shift+F9** | 面板内捕获，输出显示在「运行输出」页 | 不需要交互、想直接看结果；或需要超时保护 |
| 命令行 | `python cli.py run 你的代码.c --input "3 4"` | 脚本化 |

**编译不通过就不运行**——代码得先能编译，才谈得上运行。

#### 为什么默认改成系统命令行

一开始只有"面板内捕获"这一种：把输入**预先**喂进去。实测下来这不合适：

- 学生**不知道要先填输入框**，程序一跑就结束或拿到垃圾值，看起来就是"运行坏了"；
- 看不到"提示语 → 输入 → 输出"的交替过程，而那正是初学者要理解的东西；
- `scanf` 本来就是交互式的，把它做成"批处理"是在跟学生的直觉作对。

所以现在 F9 直接开一个真正的控制台窗口，程序跑完 `pause` 等按键，窗口不会一闪而过。

> **控制台代码页必须跟着编译器走**（实测差异）：
> MSVC 不带 `/utf-8` 时，字符串字面量按**系统 ANSI 代码页**（中文 Windows 上是 GBK）生成；
> 而 MinGW GCC 默认按 **UTF-8**。同一份 UTF-8 源码，两家的控制台表现不同。
> 所以启动脚本按编译器选择 `chcp 65001` 与否，并且**整份 .bat 按对应代码页写入**——
> cmd 是逐行读取执行的，`chcp` 之后的正文会按新代码页解释，写错编码中文提示就会乱码。

#### 运行学生代码一定会遇到的情况

| 情况 | 处理 |
|---|---|
| **死循环**（`while(1)`、忘写 `i++`） | 面板模式下超时后**连子进程树一起杀**（`taskkill /F /T`），并明确说"多半是死循环"；超时秒数可调（默认 10 秒） |
| **程序等输入**（`scanf`） | 控制台模式天然支持；面板模式用「程序输入」框一次性喂进去，没给也不会挂死 |
| **输出刷屏** | 面板模式输出限长 200KB，超出提示已截断 |
| **程序崩溃** | Windows 只给一个巨大返回码，翻译成人话（见下） |
| **中文乱码** | 控制台按编译器选代码页；面板模式按 UTF-8 优先解码 |
| **上次的窗口还开着** | **每次运行用独立工作目录**（见下） |

**返回码翻译**——学生看到 `3221225477` 等于什么都没看到：

| 返回码 | 说给学生的话 |
|---|---|
| `0xC0000005` | 读写了不该访问的内存，最常见是**数组越界**或**空指针** |
| `0xC0000094` | **整数除以 0**，检查 `a % b` 里的 b |
| `0xC00000FD` | **栈溢出**，多半是递归没有终止条件 |
| `0xC0000409` | 栈缓冲区被破坏，常见于越界写数组 |

> **三个实测踩出来的坑**
>
> 1. **BOM 会污染 stdin**：源码是 UTF-8 带 BOM 时，如果拿 `utf-8-sig` 去编码要喂给程序的输入，
>    stdin 开头就多了 `EF BB BF` 三个字节，`scanf("%d")` 直接解析失败——程序拿到未初始化的
>    垃圾值，而界面上完全看不出哪里错了。BOM 是文件层面的东西，喂 stdin 时不该带。
> 2. **解码顺序不能"谁先成功用谁"**：GBK 的字节空间很宽，几乎任何字节都能解出**某个**结果，
>    所以"GBK 解成功"不是证据；UTF-8 校验严得多，GBK 中文串几乎不可能碰巧合法。
>    必须先严格试 UTF-8。实测按源码编码优先时，程序输出的中文会变成 `תȦ` 这样的乱码。
> 3. **两种运行方式不能共用一个工作目录**（这条最坑，也是最像"运行功能坏了"的原因）：
>    上一次的控制台窗口还开着时，程序还在跑、锁着 `a.exe`，下一次编译写不进去就失败，
>    而界面只会说**"编译没有通过"**——完全看不出真正原因是"上一个窗口还开着"。
>    表现是"有时候能运行，有时候莫名其妙不能运行"。
>    现在每次运行都拿一个独立目录（`unique_workdir`，命名带**进程内递增序号**——
>    只用时间戳的话，学生连点两下会撞在同一毫秒上，等于没隔离）。

![新建项目](docs/screenshots/panel_newproj.png)

`Ctrl+N` 或工具栏「新建项目」：填项目名、选存放位置、选起始模板，
然后得到一个**文件夹 + main.c**，并直接在编辑器里打开。

### Ctrl + 滚轮 / Ctrl + 加减号缩放

| 操作 | 效果 |
|---|---|
| `Ctrl` + `=` 或 `Ctrl` + `+` | 放大 |
| `Ctrl` + `-` | 缩小 |
| `Ctrl` + `0` | 恢复默认字号 |
| `Ctrl` + 滚轮 | 在编辑器、讲解区、运行输出区都能缩放 |

缩放档位会写进用户配置，下次打开还是这个字号。

> **两个坑，第一个是"快捷键完全不生效"的根因**
>
> 1. **`QKeySequence.ZoomIn` 不是按键序列，是 `StandardKey` 枚举（值 16）。**
>    写 `act.setShortcut(QKeySequence.ZoomIn)`，PySide6 会把它当成"按键码 16"，
>    注册成 `QKeySequence(16)` —— 也就是控制字符 `'\x10'`，**快捷键静默失效**：
>    不报错、不提示，就是按了没反应。
>    同一个错误我还在 `Ctrl+O`（`QKeySequence.Open`）和 `Ctrl+S`（`QKeySequence.Save`）
>    上犯过，那两个也一直是坏的。现在一律写成 `"Ctrl+O"` 这样的显式字符串。
>    （也别指望 `QKeySequence.keyBindings(...)` 来取标准绑定——实测这个 PySide6
>    构建调用它会直接**段错误**，退出码 `0xC0000005`。）
> 2. **不能只靠 `QAction` 的快捷键。** Monaco 是内嵌的 Chromium，
>    Qt 派发按键前会先发 `ShortcutOverride`，焦点控件接受它快捷键就整个不触发。
>    所以缩放改由**挂在 `QApplication` 上的事件过滤器**接管——
>    它在事件送达焦点控件之前就能看到，绕开了这个问题，也顺带摆脱了
>    "窗口必须活跃"的前提（这一点还让快捷键**可以被自动化测试验证**）。

`QTextBrowser` 的 `zoomIn/zoomOut` 是**累加**的，所以代码里记录"已经应用了多少档"、
每次只做差值——否则来回缩放几次后状态漂移，Ctrl+0 就回不到默认了。

Monaco 那边同时保留了 `mouseWheelZoom`（作为万一过滤器没拿到事件时的兜底）；
正常路径下事件已被过滤器消费，不会双重缩放。

### 出错位置标红

只在下方给个行号，学生还得自己数行——所以直接把错误画在代码上（`engine/editorui.py`）。

| 对象 | 表现 |
|---|---|
| **正在讲的那一条** | 整行深红底 + 左侧红边 + 行号区**红点** + 具体 token 红色下划线 |
| 其它错误 | 整行淡红底 + 行号区**橙点**（让他知道"别处还有问题"，但不抢注意力） |
| 警告 | 默认不标，否则页面花花绿绿反而看不清重点 |
| 滚动条 | 右侧 overview ruler 同步打点，滚动到别处也知道哪几行有问题 |

编译通过时标红自动清空；打开另一个文件时也会清掉上一次的。

两个实现上的注意点：

1. **选中的那一条必须无条件标出来**，哪怕它是警告。否则会出现很别扭的情况：
   正在讲的是一句 `unused variable` 警告、页面上另有错误，结果别的行标红了、
   正在讲的那一行反而没标 —— 高亮和讲解对不上。（这是写测试时抓出来的真 bug）
2. **`runJavaScript(js, None)` 不合法**：PySide6 的 `runJavaScript` 有两个重载，
   显式传 `None` 当回调会让调用整个失效——表现为"代码看着没问题，标红就是不出现"。
   所以要么不传第二个参数，要么传真正的回调。

降级编辑器（Monaco 加载失败时用的 `QPlainTextEdit`）用 `setExtraSelections` 实现同样的效果，
避免这个功能在某些机器上直接消失。

两条设计约束：

1. **绝不修改学生原文件**——检查时把编辑区内容写到 `build/panel/` 的工作副本，
   编译的是副本；只有显式按「保存」才写回原文件。
2. **界面与命令行共用同一条引擎路径**（`engine.report.check_once`）与同一份分层数据，
   因此不会出现"命令行说 A、面板说 B"的分裂（有测试断言两者层结构完全一致）。

> **实测坑**：Qt 在找不到字族时会**静默把所有中文画成方块**。实测离屏渲染时
> `QFontDatabase.families()` 返回 0 个字体，整个界面全是 □。因此 `ensure_cjk_font()`
> 显式加载 Windows 自带中文字体（微软雅黑 → 黑体 → 宋体），且在 `MainWindow` 构造时就加载，
> 任何入口（测试、探针、被别的程序 import）都不会漏掉。

## 代码补全（减少打字与拼写错误）

输入前几个字母就会弹出候选，例如打 `pri` 选 `printf`、打 `for` 直接补出完整循环。

**词条是可编辑的数据文件**：`data/completion.json`（65 条，教师可自行增删）。
构成：12 个代码片段 + 25 个关键字 + 26 个标准库函数 + 2 个常量。

补全不只是省打字，**片段本身就是示范**——这是刻意的教学设计：

| 片段 | 内建的"正确范式" |
|---|---|
| `scanf` | 带 `&`（漏 `&` 是初学者最常见的运行时崩溃原因） |
| `for` | 两个分号 + 花括号（不会写成逗号，也不会漏花括号） |
| `if` / `else` | 完整的配对结构（避免 if 后误加分号导致 else 悬空） |
| `main` | 标准 `int main(void)` 写法 |
| `swap` | 借助第三个变量（不会写出互相覆盖的错误交换） |
| `include` | 下拉可选 stdio.h / stdlib.h / string.h / math.h |

每条都有中文说明，鼠标悬停能看到"这是什么、容易错在哪"。

> **实现说明**：qtmonaco 打包的 JS 只为 `python` 硬编码注册了补全提供者，而且
> `globalAPI: false`（`window.monaco` 不存在）。这里通过**子类覆盖
> `Monaco._load_editor()` 注入自己的模块脚本**来实现——不修改第三方包，
> 升级依赖不会被覆盖。注入脚本里 `import('./assets/monaco-core.js')` 拿到的
> 导出中 `r` / `m` 即完整的 monaco 命名空间（压缩后名字，实测得出）。
>
> 另一个实测坑：`runJavaScript` 的执行上下文 base URL 是 `about:blank`，
> **在 Python 侧无法 `import()`**；因此必须由页面内脚本把 `monaco` 句柄挂到 `window` 上，
> 外部才能用它做自检。

### 什么时候会调用、花多少钱

只在**本地知识库没有收录**这个错误码时才调用一次。命中时零成本零延迟。

实测（deepseek-flash）：单次解释 `tokens in=718 out=248`，其中 **512 个 token 命中上下文缓存**，
成本约 **0.0015 元**；缓存命中价 $0.003/M 与未命中 $0.15/M 相差 50 倍，
所以系统提示被刻意做成字节稳定的前缀（有测试断言其 sha256 不随输入变化）。

### 安全与质量上的约束（都有测试）

- 发送前**脱敏**本机路径、邮箱、疑似密钥
- **位置只来自编译器**——模型返回的任何行号/文件名一律丢弃
- 模型输出必须通过 JSON schema 校验；失败重试一次，再失败**降级为只给定位**
- 输出完全不是 JSON 时**失败关闭**，不展示未经校验的自由文本
- **答案泄漏守卫**：剥离完整可复制的代码解法（文献实测模型 48% 会违规）
- 所有界面/日志里只出现**打码**后的密钥

## 三步开发的内容

**第一步 本地报错解释器**：编译 → SARIF 解析 → 中文知识库匹配 → 本地讲解，完全不联网。

**第二步 分层讲解**：一条诊断讲成 5 层（结论／定位／原因／改法／知识点），`--depth 1..5` 渐进披露。
默认 4 层——本工具的本职就是给出明确的修改意见。

**第三步 接入 DeepSeek**：只在本地知识库未命中时调用；稳定前缀吃上下文缓存；JSON 校验 +
重试 + 降级；答案泄漏守卫；位置锚定；发送前脱敏。

## 实测发现的两个中文专属陷阱（英文环境永远遇不到）

这两个都是**只在中日韩源码上出现**的问题，纯英文测试完全测不出来。

### 1. MSVC 的列号模型：ASCII 宽 1，双字节字符宽 3

受控实验（0~4 个汉字）结果：

| 汉字数 | 字符列 | 字节列(GBK) | MSVC 列 |
|---|---|---|---|
| 0 | 16 | 16 | 16 |
| 1 | 17 | 18 | 19 |
| 2 | 18 | 20 | 22 |
| 4 | 20 | 24 | 28 |

即 `列 = 字符列 + 2 × 之前出现的双字节字符数`。纯 ASCII 行两种模型一致，
所以**按字符列直接画插入符，每遇一个汉字就会偏 2 列**。已修（`encoding.col_to_char_index`），
并有端到端回归测试：0~4 个汉字行的插入符都必须落在 `int x` 上。

GCC 侧我们传了 `-fdiagnostics-column-unit=byte`，列号是字节偏移，走另一条换算路径。

### 2. MSVC 的 SARIF 会含被截断的多字节字符

SARIF 里带一个 `snippet` 字段，装着源码行的**按字节截断**片段。源码含中文时截断点可能
落在多字节字符中间：

```json
"text": "    int x = 10\xef\xbc"     ← 三字节的「；」被切掉最后一字节
```

于是**整份 SARIF 不是合法 UTF-8**，严格解码直接失败。已修：容错解码（结构完好，
只有那半个字符降级为 U+FFFD），并有回归测试确认错误码与行号依然正确。

## 知识库是怎么长起来的

第一版 27 + 25 条是按调研方案手工写的。之后分两轮扩充到 61 + 53 条，
**每一轮的来源都不同，可信度也不同**：

| 轮次 | 来源 | 可靠性 |
|---|---|---|
| 第一版 | 调研方案（c-error-helper 等开源规则）+ 人工撰写 | 中 |
| 第二轮 | `tools/probe_snippets.py` 对 **MSVC 14.51 / GCC 16.2 的真实编译实测** | **高**（码是编译器自己报的） |
| 第三轮 | 三个并行调研：英文社区高频清单、中文社区与中国高校材料、开源知识库审计 | 参考（需实测确认） |

**经验教训：网上抄的错误码经常对不上。** 调研报告里说"全角空格报 C3872"，
我实测得到的是 **C2065**（因为编码和上下文不同）。所以现在的规矩是：
**写进知识库的每个码，先用 `tools/probe_snippets.py` 实测确认。**

### 调研里最值得记的三条

1. **"烫烫烫"不是隐式类型转换。** 中文社区有篇文章的摘要这么写（错的），
   真因是：缺 `\0` + VS Debug 用 `0xCC` 填充栈 + GB2312 把 `0xCCCC` 显示成"烫"。
   有意思的是**同一篇正文解释是对的**——"摘要错、正文对"正是 RAG 类工具最容易踩的坑。
2. **"无脑把 scanf 换成 scanf_s"是社区流行建议的恶果。**
   `%c` 必须额外传长度参数（`scanf_s("%c", &c, 1)`），大量教程只教"加个 `_s`"，
   结果学生换完崩得更厉害。
3. **教材用 `gets()` 必然编译不过。** 微软 C3861 官方文档的示例**直接就是 `gets()`**——
   这从编译器侧官方证实了"老教材代码在新 VS 上报错"不是学生抄错了。

### 中文特有问题单独处理

这些是英文项目结构上覆盖不到的，也是本项目存在的理由：

- **全角标点**（U+FF1B 等）：MSVC 说"数字上的错误后缀"、GCC 16 说 `invalid suffix '；'`
- **全角空格 / 不间断空格 / 零宽字符**：**最坑的一类**——报出来是
  `C2065 "x": 未声明的标识符`，看起来像拼写错误。本工具会：
  - 直接指出"这一行里有看不见的字符"，并给出列号
  - 当报错消息里的名字是**乱码**（`鈥渉i鈥`、`int聽a`）时，
    额外提示"问题不在拼写，在字符/编码"——因为按拼写方向查永远查不出来
- **编码错位**：C4819 / GCC 的 `stray` 系列

### 错误雪崩：一次报几十条不代表错了几十处

编译器经常一次喷几十条错误，但它们绝大多数是**第一条的连锁反应**。
本工具只讲第一条，并且在错误数 ≥3 时明确提示：

> 一次报很多条通常**不是很多个错误**——第一条往往是根因，
> 修好它之后后面那些多半会一起消失。先只改下面讲的那一处，再重新检查。

### 选哪一条讲：一个被测试逼出来的修正

规则是"有错误取第一条；只有警告时挑最值得讲的"。第二条最初写成
"挑**本地知识库能解释**的那条"——在知识库还小的时候**碰巧**能用，
因为噪音条目还没被收录、会被自动跳过。

知识库一大，`unused variable` 也被收录了，它立刻抢走了讲解位置：
学生问"函数为什么报错"，得到的是"变量 s 没用到"。

**修正：把"没用到"这类噪音警告排到后面，先按"这条警告像不像真缺陷"排序。**

> 教训：**"我们能解释"和"这条值得讲"是两件事，不能用前者代替后者。**

真实 API 实测（deepseek-flash）：未收录错误由 AI 补齐三层讲解，位置仍来自编译器；
`tokens in=718 out=278，上下文缓存：命中 512 / 未命中 206`；单次约 **$0.0002**。
知识库命中时**完全不调用模型**。

## 两个编译器后端的实测差异

GCC 与 MSVC 对同一个错误的报法完全不同，本项目两个后端都已用真实编译器验证过
（GCC 16.2.0 / w64devkit、MSVC 14.51）。代表性的差异：

| 场景 | MSVC | GCC |
|---|---|---|
| 漏分号 | `C2146 缺少";"` | `expected ',' or ';' before 'printf'`（**无错误码**） |
| 全角分号（GBK 源码） | `C2059 语法错误:"数字上的错误后缀"` | `stray '\243' in program` |
| 漏 `#include` | `C4013`（**仅警告**，程序照跑） | `-Wimplicit-function-declaration`（**错误**） |
| `main` 拼错 | `LNK1561`（文本，不进 SARIF） | `undefined reference to 'main'`（文本，无行号） |
| 变长数组 `int a[n]` | `C2133/C2057` **报错** | **合法，无诊断** |
| `scanf` 漏 `&` | `C4477` + `C4700`（警告） | `-Wformat` + `-Wuninitialized`（警告） |

> 倒数第二行值得单独说：**同一份代码在 GCC 上能跑、在 MSVC 上报错**——
> 这正是学生"在我电脑上没问题，交上去编译不过"的典型来源。
> 样本集里刻意保留了它作为对照。
>
> GCC 侧还有一个实测坑：诊断没有关联警告选项时，它会把 SARIF 的 `ruleId`
> 写成级别本身（`"error"`），而不是规则标识符；部分警告还会带一个多余的尾随等号
> （`-Wformat=`）。两者都已在解析层归一化。
